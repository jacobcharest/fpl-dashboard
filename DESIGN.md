# FPL Dashboard — Design Notes

Local-only dashboard for visualizing Fantasy Premier League player/team data across seasons.
This file is the source of truth for decisions made during planning, so later work doesn't
depend on chat history.

## Stack (locked)

- **Backend**: Python + FastAPI, SQLite storage (`data/fpl.db`, gitignored — regenerated by scripts).
- **Frontend**: React + TypeScript (Vite), TanStack Table (sorting/sticky header+column/filters),
  Plotly.js (all chart types).
- Runs locally as two dev processes (`uvicorn` on 8000ish, Vite on 5173) during development;
  later can be bundled into a single process serving the built frontend.
- Repo: public, `jacobcharest/fpl-dashboard` on GitHub.

## Data sources (verified against live data, see chat history for raw checks)

- **Official FPL API** (`fantasy.premierleague.com/api/...`, no auth): `bootstrap-static/`,
  `fixtures/`, `element-summary/{id}/`. Used for the **current season, live** — refreshed
  on-demand via a "Fetch new data" button (weekly cadence, manual trigger, no scheduler needed).
  `element-summary` only gives gameweek-level history for the *current* season; past seasons
  there are season-total-only.
- **Historical archive**: [vaastav/Fantasy-Premier-League](https://github.com/vaastav/Fantasy-Premier-League)
  GitHub repo — per-gameweek CSVs for **2016/17 through 2025/26** (10 seasons). Used for one-time/
  occasional backfill via `backend/scripts/backfill_history.py`.
- **Column availability by season** (confirmed by inspecting real CSVs):
  - xG / xA / xGI / xGC / `starts`: available from **2022/23** onward only.
  - Defensive contributions: available from **2025/26** onward only (brand-new FPL stat).
  - Decision: all 10 seasons stay selectable in the season dropdown; unavailable columns are
    blank/N/A for seasons before they existed (not hidden, not defaulted away).
- Team-level xG/xGA has no direct source field — derived by summing player-level
  `expected_goals` per fixture, grouped by team.
- **Identity keys**: FPL reassigns team `id` and player `id` per season (alphabetical
  team ids, etc.). Stable cross-season identity is the `code` field for both. Schema keys
  on `team_code` / `player_code`; season-specific ids are only join keys during ingestion
  (see `player_season.season_element_id`, `teams.season_team_id`).

## Schema

See `backend/app/schema.sql`. Core fact table is `player_gw_stats` (one row per player per
fixture). Team standings, xG aggregates, per-90 conversion, and filtered stats are all
**computed at query time**, not stored — the full dataset (~250k player-gameweek rows across
10 seasons) is small enough that this stays fast (single-digit ms) with proper indexing.

## Filter semantics

- Left panel: every team in the selected season, each with an include/exclude checkbox and its
  own gameweek-range (two inputs). Global "include all" / "exclude all" buttons and a global
  gameweek-range input that, when set, applies to all teams at once — but is an "apply then
  override" action, not a persistent link. Editing one team's range afterward doesn't fight
  with the global input.
- Separate include/exclude-as-**opponent** checkbox per team — restricts rows to fixtures played
  against included opponents.
- Player rows are filtered/sliced using *that player's own team's* gameweek range (e.g. Arsenal
  set to GW3-7 → Declan Rice only shows GW3-7 rows), further sliced by the opponent filter.
- These filters apply identically to both the player table and the team table.
- Player-table-only toggles: per-90 normalization, starts-only (excludes an unstarted or
  substitute appearance entirely, not just zeroed).
- Per-column numeric filters (>/<) on top of click-to-sort. First column and header row are
  frozen on both tables.

## Table columns

**Player table**: name (frozen), price, total points, minutes, goals, xG, assists, xA, xGI,
clean sheets, xGA, defensive contributions, bonus points.

**Team table**: name (frozen), table place, goals, xG, goals against, xGA, goal difference,
opponent xG, opponent xGA.

- `xGA` on the team table = actual expected goals conceded by that team (sum of opposing
  players' `expected_goals` in their fixtures).
- `opponent xG` / `opponent xGA` = strength-of-schedule metrics, distinct from the above: for
  each fixture a team played within the filtered gameweek range, take that specific opponent's
  own average xG-per-game (or xGA-per-game) computed **within that same gameweek range**, then
  average across all of the team's fixtures in range (an opponent faced twice counts twice).
- "Table place" is computed from results **within the filtered gameweek range** (a mini-league
  table for that window), consistent with everything else being filter-scoped — not the live
  season-long league position.

## Chart builder

Dropdown of chart types; picking one reveals a second "choose data" step (entities, stat(s),
type-specific options). Charts **inherit the table's current filter/toggle state live** (season,
included teams, per-team ranges, opponent filter, per-90/starts-only) rather than freezing at
creation time — changing a table filter updates open charts.

| Type | Data step |
|---|---|
| Time series | stat, entities (multi-select), cumulative vs per-gameweek |
| Scatter | stat X, stat Y, entities; optional y=x reference line (auto-suggested for actual/expected pairs) |
| Ranked bar | stat, top N or all, sort direction |
| Radar / spider | entities (2-5), stats (multi-select), raw vs percentile-normalized |
| Heatmap | entities, stat (grid = entity × gameweek) |
| Distribution / box plot | stat, entities highlighted as points against the filtered pool |
| Stacked breakdown | single entity, raw per-gameweek counts (goals, assists, clean sheets, bonus, defensive-contribution-met) — **not** exact point-value decomposition (scoring rules are position-specific and changed across seasons; not worth hardcoding) |
| Small multiples | stat, entities (sparkline grid) |

"Value" (points added per price added) is a **derived stat** usable anywhere a stat is picked
(e.g. in Ranked Bar or Scatter), not a standalone chart type:

```
base_price = {GK: 4.0, DEF: 4.0, MID: 4.5, FWD: 4.5}
steps = (current_price - base_price[position]) / 0.5      # normalized to £0.5m increments
value = total_points / steps   if steps > 0
value = N/A ("∞")              if steps == 0  (sorts to the top — undefined marginal return,
                                                not faked with an epsilon denominator)
```
Step-normalizing (not raw £m) matters: with raw price difference as the denominator, a player
one £0.5m step above base would double their score relative to a player two steps up — an
arbitrary jump. Steps make step 1 the neutral baseline.
